# dp-cj：短视频文案提取入库

本 skill 只负责三件事：**确认分类表 → 提取视频文案与元数据 → 按对应表字段写入飞书 Base**。不生成改写稿，不创建云文档，不维护额外个性化资料。

## 强制前置提问

只要用户发送视频链接或分享文案，第一条回复必须先询问分类，**不得立即提取、转写、加工或写库**。即使用户在发链接时顺便猜了一个分类，也必须等用户明确确认后再执行。

固定提问：

```text
请确认这条链接要放入哪张表：
1. 工厂实体店
2. 情感(泛流量)
3. 自媒体+AI
4. 搞钱(干货)
5. 人设
6. 营销
7. 情感共鸣型（泛流量）

回复表名或编号即可。确认前我不会开始提取或入库。
```

用户必须明确回复以下名称之一，或回复编号 1–7（保留旧编号，新表追加为 7）：

- 工厂实体店
- 情感(泛流量)
- 自媒体+AI
- 搞钱(干货)
- 人设
- 营销
- 情感共鸣型（泛流量）

「情感共鸣型(泛流量)」与全角括号写法视为同名；它与第 2 项「情感(泛流量)」是两张独立表，不能合并或互相代替。

如果回复含糊、出现多个分类或要求“你帮我判断”，继续询问，不执行任务。

## 执行流程

### 1. 确认目标表

用户确认分类后，从 `feishu.tables` 取得对应 `table_id` 和 `field_map`。不要把内容写入其他表。

每次写入前实时读取目标表字段和单选选项，以真实结构为准。新表「情感共鸣型（泛流量）」ID 为 `tblbnZuCHc3K7qDc`；目前与工厂实体店表一样有「行业」，没有「文案类型」。不复制其他表的整套字段后盲写。

### 2. 提取

链接/分享文案：

```bash
<python_executable> scripts/douyin_transcript.py --config config.json --category "<用户确认的分类>" --payload-out "_tmp/payload.json" "<链接或分享文案>"
```

本地媒体：

```bash
<python_executable> scripts/douyin_transcript.py --config config.json --category "<用户确认的分类>" --payload-out "_tmp/payload.json" --file "<文件>" --author "<作者>" --link "<原链接，如有>"
```

读取输出的 Markdown 与 `[payload]` JSON，自动取得标题、作者、发布时间、时长、互动数据、封面和口播全文；优先使用 JSON payload，避免手工抄写统计字段。机器转写写入前只校正明显的同音字、领域词和断句错误，不改写原文；报告中注明“已做最小转写校对”。链接模式优先官方字幕，其次音频流语音识别，再从视频音轨识别，最后才用 OCR 硬字幕兜底。

### 3. 填字段

只填写目标表已有字段，详见 `references/field-extraction.md`：

- 标题
- 文案全文
- 开头+金句
- 选题
- 行业（按下方规则判断，写入一个规范行业名称）
- 链接
- 平台
- 发布日期
- 视频时长
- 点赞数
- 评论数
- 收藏数
- 分享数
- 文案类型（选中分类与该字段一致；工厂实体店没有此字段则不填）
- 原始内容类型（仅搞钱(干货)表有；仅在输入或元数据明确提供时填）
- 封面 / 标题截图 / 赞藏截图（封面按下方校验规则取作品实际展示封面；截图只有提供本地文件或 URL 时才上传）

#### 行业：先识别主营业务，再归到规范单选项

读完整文案，判断这条内容主体实际经营、生产或销售什么。把店型、产品和细分业态归到同一层级的行业：火锅店、卤味店、酥肉面馆、烧烤店 → 餐饮；女装店、男装店、童装店 → 服装；门窗厂、系统窗、铝合金门窗 → 门窗；五金店、五金配件 → 五金；瓷砖店 → 瓷砖；纸箱厂、飞机盒 → 纸箱。行业不是内容类型；「情感共鸣」「营销」「工厂」「实体店」不能当行业。

以文案中主营业务的直接表述为依据；标题、账号名仅作交叉核对。不能因为出现「吃火锅」就把服装店归餐饮，不能因为门窗厂讲五金配件就改归五金，也不能把「我不做餐饮，我做门窗」判为餐饮。多行业举例时找内容主角；确实没有单一主体或没有行业信息时不猜、不强填「其他」。

对有「行业」字段的表，补入 payload：`industry`（单个字符串）和 `industry_evidence`（文案全文中的原句）。先匹配实时单选项；细分类合并到已有标准项，不另建「火锅店」等同义项。若明确是尚未收录的新行业，在用户已授权的入库任务内补充对应标准单选项，保留原有选项，再读回核对后写入；不要把它硬塞到无关行业。字段不是单选时先报告结构不符，不按文本或多选强写。

确实无法判断时，省略 `industry`，设置 `industry_status: "undetermined"` 和 `industry_reason`，报告待补原因；更新已有记录时保留旧行业。没有「行业」字段的表跳过该字段，不自行新增列。细则和反例见 `references/field-extraction.md`。

#### 封面：作品身份和展示内容都要核对

1. 元数据 `aweme_id` 必须等于目标链接解析出的作品 ID；作者、标题也要吻合。错误跳转、推荐视频或作者列表中的其他作品不能使用。失败仅做一次有依据的重试，仍不匹配就报告缺口。
2. 视频优先 `dynamic_cover`，其次 `cover_original_scale`；图文取同一作品的 `images[0]`。这来自已验收样例，不表示所有作品的字段永远同义。下载后实际查看图片，确认是该作品展示封面；无贴字封面也可能正确，不能擅自加字。
3. 不再使用 `origin_cover` 自动兜底，不从视频抽首帧替代；`cover` 或网页 poster 可能是横裁图，仅可辅助核对，未经确认不能当完整封面上传。不按元数据宽高评分、不为了统一竖版而裁剪、不自行改 CDN 签名 URL。只剩这些候选时留空或保留旧附件，报告封面待核。
4. 只有实际看过并核对无误后，才在 payload 标记 `cover_verified: true`，填写 `cover_source` 和 `cover_verification_note`（核对的作品 ID、人物/场景、与展示封面的对应依据）。自动提取出的 URL 只是候选，不代表验收通过。看不到图片时不能宣称已目视确认。
5. 更换附件必须先成功上传新图，再删除上传前记录的旧 token，最后读回核对仅保留新图。任何一步失败如实报告；不能把命令已发出当作成功，也不能先删旧图再尝试下载新图。

“开头+金句”格式：

```text
开头：{原文第一句}
金句：
1. {原文金句}
2. {原文金句}
```

### 4. 写入

payload 必须包含用户确认的 `category`：

```bash
<python_executable> scripts/write_record.py --config config.json --payload "<payload.json>" --dry-run
<python_executable> scripts/write_record.py --config config.json --payload "<payload.json>"
```

脚本会按分类选择对应表、映射字段，并按“链接”查重：同一链接更新原记录，不新增重复行。

### 5. 报告

报告分类表、标题、行业（或待补原因）、来源链接、写入动作、封面核验结果和 Base 链接；有缺口明确说明，不把部分完成说成全部成功。不得展示内部 JSON、token、会话字段或调试日志。

## 边界

- 只做提取与字段入库，不做洗稿、改写、润色、选题策划或文案创作。
- 没有用户分类确认，不得执行任何提取或写入。
- 表内不存在的字段必须跳过，不自行新增列。
- 附件无法可靠取得时留空或保留已有附件；只有身份和展示内容核验通过的封面才上传。
- 配置中的工作区路径属于使用者本地环境；共享 Base 地址由 `config.example.json` 提供。
